# N1 automation: shared authoring, synchronization and recovery contract

Effective 2026-09-23. Read this document and policy.json before every 09:00, 11:00 or recovery invocation. These rules consolidate existing requirements; no content, evidence, dedupe, privacy or deployment gate is weakened. Technical source schemas and the upstream learning-review module remain authoritative for their fields.

## Entry points and durable state

09:00 creates the original; 11:00 prepares the synchronized lesson; N1 recovery runs ONCE daily at 12:00 Asia/Tokyo, never hourly. The plan is 2026-08-30=Day1 through 2026-12-06=Day99. After the end, do not create Day100, a negative countdown or a replacement plan without approval. Recovery may still finish pending in-plan dates. Recover every due date from 2026-09-19 plus earlier explicitly pending dates, using a complete calendar/file inventory, not just existing files. Read failures or truncation are not proof of absence.

Normal sync, recovery and upstream handoff submit the SAME complete `.github/n1-sync-request.json`; `.github/workflows/sync-n1-daily.yml` is the normal writer of final daily JSON and snapshot. Do not maintain another normal direct-to-JSON writer. Before submitting a request, inspect live sync and Pages runs; do not replace an active request. Preserve pending dates in `automation/n1-progress:runs/DATE/sync-status.json` and completed request drafts in `runs/DATE/request.json`. One shared request slot is not a durable queue. Drain oldest pending dates without discarding another date's request; freeze targetDate across midnight.

Request-file pushes start the workflow. workflow_dispatch/repository_dispatch may replay a matching, already complete request. A callback is only a hint; it cannot create missing lesson content or rebind an old request to another commit/date. waiting_request/waiting_matching_request is not publication success.

## Checkpoint the exact original before promotion

Read n1-plan.md. Generate the complete public teaching text once: original immersion material, learning plan, minimum completion line, adjustment conditions and 3–5 review questions. Do not put individual scores, private answer history, fatigue/health details, email or private tool records in the public repository, including progress branches. Keep personalized feedback outside the public teaching text in the private response/store.

Stage exact final source bytes, not a summary:

```sh
node scripts/n1-automation.mjs stage YYYY-MM-DD 'REAL_TIMESTAMP+09:00' /tmp/source.md /tmp/source.json
```

Create automation/n1-progress once from known main if absent; never force-reset it. Save this record as runs/DATE/source.json on that branch using latest blob SHA/CAS. Read back and verify targetDate, Day, bytes, sha256, real timestamp and exact markdown. A different existing original is a correction conflict, not permission to regenerate. Do not invent an old generatedAt timestamp.

```sh
node scripts/n1-automation.mjs restore /tmp/source.json /tmp/n1-checkout
```

The helper creates only n1-source/DATE.md, does nothing for identical bytes and refuses to overwrite another original. Commit those exact bytes to main with latest SHA/non-force protection; read back and compare the checkpoint hash. This helper performs local validation/materialization, NOT GitHub API calls: use actual discovered connector actions for remote writes. A verified outbox plus failed main write means source_pending_promotion, not source_saved. Send the same public teaching text to the user; status/private commentary is separate.

At 11:00/noon, when main source is missing, recover the complete outbox record, verify and promote it before mapping. If neither original nor checkpoint is readable, keep source_missing; never reconstruct from memory, templates, yesterday or excerpts. If all authorized persistence fails during authoring, still provide the full lesson and a real full-text attachment; state that no recoverable remote record exists. A later task cannot be assumed to read an unattached local path. Use at most three evidenced transient attempts; never bypass 401/403 or leak private data to a public fallback.

## Shared upstream lease and publication handoff

EVERY upstream writer, including N1 tasks, first reads the current kai987/japan-it-ai-daily docs/daily-publication/README.md, docs/automation/README.md, scripts/daily-publication.mjs and scripts/daily-publisher.mjs, then uses claimLease/renewLease/assertLease with automation/daily-progress:locks/publisher.json. Latest SHA/CAS plus token read-back;45minTTL, renew at least every5min. Unreadable/live foreign locks prohibit writes. Acquire upstream before N1 request ownership; do not hold one repository while waiting for the other.

Since the upstream P1 architecture effective 2026-09-24, N1 sync/recovery MUST NOT directly write the six IT daily publication paths to upstream main. Any upstream repair follows the same author flow: checkpoint -> draft/daily-YYYY-MM-DD -> exact green deploy.yml preflight -> durable request_ready state -> CAS write automation/daily-publish-request:.github/daily-publication-request.json -> unique publish-daily.yml. If that publisher is queued/in_progress, yield and do not replace its request. Only the publisher may normally fast-forward those daily paths to upstream main; then verify the exact final main deploy.yml/Pages/post-deploy snapshot before treating the upstream repair as published. Release the upstream author lease after durable request submission/ownership transfer according to the upstream runbook, then continue N1 only after verified publication.

Read failed run/job/step logs first, fix only evidenced direct causes and add regression tests. Never weaken schema, evidence, history, bilingual, quality, browser or security checks. Preserve unknown root causes as unknown.

After a NEWLY verified publication, the IT primary/recovery task performs this same handoff once if the corresponding N1 original exists and the date is pending. This is publication continuation, not an hourly N1 scan. If sources are missing, record the handoff blocker for the existing daily entrypoints. A separate optional GitHub success callback replays matching ready requests and requires cross-repository credentials; absent credentials or missing requests must never be called end-to-end automatic success.

## Incremental audio follow-up

Effective 2026-10-19. The text request, source binding, schedules and two-file text commit allowlist above remain unchanged. Audio is a separate continuation, never another writer of daily JSON, N1 originals or the IT snapshot.

After successful N1 main Pages deployment, `sync-n1-audio.yml` locks a successful main `kai987/japan-it-ai-daily/.github/workflows/sync-r2-audio.yml` commit and reads only its manifests. It matches the complete normalized utterance, morioki / ノーマル (497929760), model, speed, intonation and sample rate. New shared clips require a complete public R2 GET, exact SHA-256, decoded duration and non-silent PCM. Already verified hosted recordings remain intact. No MP3 is added to Git or the Pages build. `src/data/audio-pending.json` records all missing utterances and their lesson/card references; a green workflow with pendingClips > 0 is not complete audio coverage.

N1 and upstream audio may finish in either order. After the local IT task has verified the exact upstream audio commit's R2, Pages and playback, invoke this once for the frozen date and commit:

```sh
gh workflow run sync-n1-audio.yml --repo kai987/Japanese-N1-Immersive-Sparring-Partner --ref main \
  -f target_date=YYYY-MM-DD -f source_audio_commit=FULL_SUCCESSFUL_R2_COMMIT
```

Inspect the exact follow-up run and resulting N1 commit/Pages; `waiting_n1_lesson` means the existing N1 daily entrypoint must finish the lesson first. A completed N1 Pages run then retries the shared audio step. Resume failed/pending audio during existing daily invocations even if text is unchanged, without resending a text request or adding an hourly schedule. No cross-repository token or new storage credential is required for reading public manifests and audio. The local task needs its existing GitHub authorization to dispatch the N1 workflow; the upstream optional text callback is still unconfigured unless its own token is actually present.

Unique N1 sentences are handled by the deterministic local audio worker (`scripts/audio-worker.ts`). Effective 2026-10-20, the macOS LaunchAgent `dev.kai987.n1-audio-worker` checks only during 11:10–13:10 Asia/Tokyo, every 15 minutes: 11:10, 11:25, 11:40, 11:55, 12:10, 12:25, 12:40, 12:55 and 13:10. Calendar scheduling requires the Mac system time zone to remain Asia/Tokyo; the bootstrap and worker independently enforce Tokyo time before any Git/network checks. Login/load and wake catch-up also obey this window. The final check minute ends at 13:11; an active job is then cancelled with its verified progress retained.

Once today's lesson or unfinished audio is detected and processing begins, an atomic `~/Library/Application Support/N1 Audio/schedule.json` latch suppresses all later checks that Tokyo date, even after failure, upstream-audio waiting or a restart. The next Tokyo date automatically becomes eligible; unfinished jobs resume at the next day's 11:10 opening (or the next available check). Empty checks and pre-detection network failures leave the day unclaimed and may retry at a later slot. `progress.json`, `uploads.json` and generated candidates remain intact across pauses; zero pending uploads does not mean validation/deployment is complete. `npm run audio:auto` observes the same window, latch and OS lock, without a force override. Inspect the checkpoints and logs outside the window without triggering remote checks. Keep the original 09:00/11:00/12:00 text entrypoints and local IT daily task unchanged in time; never fall back to browser upload or add another LLM recovery schedule.

A separately authorized foreground repair may use `npm run audio:repair -- --dates YYYY-MM-DD,YYYY-MM-DD --evidence-dir /absolute/private/evidence`. This explicit transaction keeps the same OS lock and all immutable-upload, validation, normal-push and exact-Pages gates; it refuses missing speech outside the requested lesson dates. It does not change LaunchAgent, reset schedule.json or delete generated cache. It has a two-hour bound and stores full validation stdout/stderr and Playwright reports outside disposable attempts. The normal audio:auto/bootstrap remain time/latch constrained; do not invoke this repair from scheduled entrypoints or without explicit authorization.

The worker freezes current N1 main, the complete speech catalog, and a successful upstream R2 commit. If a new lesson's daily manifest is not ready it records waiting_daily_audio, so it does not synthesize shared words prematurely. It verifies shared utterances first and preserves every existing hosted mapping. Only missing N1 utterances are synthesized with the pinned morioki model. `generate-audio.py --plan PATH --work-dir PATH` writes candidates, per-clip sidecars and license in the private service cache; it never changes published metadata mid-generation. Completed clips survive interruption, an engine patch does not invalidate the same model, and a different model requires explicit repair rather than regenerating history.

Uploads use only `n1-audio-upload`, a fixed-bucket Edge Function. A 256-bit local capability is stored by the compiled `scripts/keychain-audio.swift` helper in macOS Keychain; only its SHA-256 is in the deployed/public configuration. Function authentication runs before reading bytes. The function permits only immutable `morioki-normal/ID--SHA256.mp3` creation in `n1-audio`, validates actual SHA/MP3/type/size, and cannot overwrite, delete, list or access another bucket. Server keys remain in Supabase's runtime environment; neither browser sessions nor broad project credentials are exported to the Mac. Existing interview bucket privacy and policies remain unchanged. Before treating deployment as configured, test unauthorized denial, authorized idempotence, forbidden bucket rejection, and real new-byte upload plus public verification.

Every upload attempt starts with a full public GET/hash/size check, so a lost POST response or local-cache deletion after verified publication cannot cause duplicate uploads. Network/429/5xx failures receive bounded backoff inside the active job, then remain retry_pending until the next eligible day once detection has claimed today. Window cancellation aborts in-flight upload requests without retries, retaining byte-verified upload proofs and candidates. Auth/config/model failures preserve candidates for repair and later resume; do not replace voices or suppress validation. Complete upload proofs are merged into four metadata files in an isolated attempt checkout. Dependencies receive a completion marker only after installation succeeds; tests/build/browser playback use an isolated preview port. Fetch latest main immediately before normal push; a race preserves candidates and remerges against new main on the next eligible day, never force-pushing or modifying the user's checkout. A previous deployment must not pin recovery forever after main advances. A clean/no-change retry still verifies a new release's exact Pages result before reporting complete. Only verified published local MP3 caches may be deleted.

Installation: deploy `supabase/functions/n1-audio-upload` with the configured capability hash and `verify_jwt=false` (the function performs its own authentication), then run `npm run audio:worker:install` on the Mac. Re-run that installer after calendar/bootstrap changes; it preserves the credential helper, candidates and progress while replacing this agent's schedule. It does not change other agents or daily schedules. A Mac that is shut down, offline, or has not unlocked its login Keychain cannot execute local synthesis; persisted state resumes in the next eligible time window after its environment returns. Progress and logs are local, contain no tokens, and are independent of public lesson metadata.

Audio-only automated commits permit exactly `public/audio/manifest.json`, `src/data/audio-index.json`, `src/data/audio-sources.json`, `src/data/audio-pending.json`, with the same `n1-content-sync` concurrency group, current-main fast-forward check, no force push, and explicit Pages dispatch only after a change. Use `audio:validate -- --snapshot` for a published snapshot while newer dates are pending; use plain `audio:validate` to claim full current coverage. Delete local MP3 caches only after full remote byte verification; keep the manifests and voice license.
